# 实盘观测运行手册

这个目录里的脚本**不改动 `src/` 的任何业务逻辑**，只从 `/api/export` 读数据。雷达仍然是原样运行的只读扫描器。

## 组成

| 文件 | 作用 |
|---|---|
| `snapshot.mjs` | 抓一次 `/api/export`，按天存成 `snapshots/YYYY-MM-DD/export-<epoch>.json.gz` |
| `analyze.mjs` | 读全部快照，输出每项 check 的失败率、以及经幸存者偏差校正的影子表现 |

## 为什么必须抓快照

雷达自身会按保留期裁剪状态，不抓就永久丢失：

| 数据 | 保留期 |
|---|---|
| `candidates`（含 `deep.checks` / `deep.failed`） | 2 小时（`candidateRetentionMs`） |
| `outcomes`（影子样本） | 7 天（`outcomeRetentionMs`） |
| `events` | 最近 500 条 |

## 频率

**10 分钟一次。** 理由不是数据量，是 `toPublicStatus` 对 `candidates` 做了 `slice(0, 100)`，而排序是 `X_REVIEW > WAIT_RECHECK > HARD_REJECT`。

**这是本方案已知的最大局限：当某一轮的候选数超过 100，被截断的总是 HARD_REJECT 那一批。** 也就是说重建出来的 per-check 失败率会**低估**硬拒绝相关的项。10 分钟的间隔是为了在列表被填满之前就抓到刚审完的币，缓解但不能消除这个偏差。

要彻底消除，只能在 `scanner.cycle()` 里加一个累计计数器（约 10 行），代价是改动业务代码。当前选择的是不改。看报表时请记住这一条。

## 分析脚本的两个输出

### 1. 每项 check 的失败率

关键是最后一列 **「未知占失败」**：

- 接近 100% → 该项卡在**数据缺失**上，调阈值没有意义，要么是这条链不返回该字段，要么是数据处理太严
- 接近 0% → 该项**真的在筛币**，阈值调整才有效果

去重口径是 `chain:address:reviewRevision`。`reviewRevision` 是服务端对所有被判定字段的哈希，所以同一个结论在多份快照里只算一次，但真正的重新审计会算作新的一次。

### 2. 影子表现的保守/乐观区间

代币 rug 之后没有成交、没有 K 线，取价失败，在雷达自身的统计里表现为「缺失」而不是「极低收益」——所以原始的中位涨跌是**系统性向上偏**的。

脚本对每个窗口做删失判定：观测时间已超过到期时间 3 小时以上、该窗口始终没有取到价、且**所有更晚的窗口也都没取到价**（更晚的窗口有价说明币当时还活着，那就是数据缺口不是死亡）。

满足条件的记为 `censoredLow`，然后：

- **乐观中位**：只看已观测样本（= 雷达自身的口径）
- **保守中位**：删失样本排在所有已观测值的**下方**。中位数是序统计量，只需要排序不需要数值，所以**不编造任何收益数字**
- 若输出 `<死亡区>`，意味着中位数本身落在删失区间内 —— 此时任何正的乐观中位都是纯粹的幸存者偏差产物

`p90滞后` 列是 `|at - targetAt|` 的 90 分位。雷达有两条取价路径：精确路径取 ±60 秒内的已收盘 1 分钟 K 线，机会路径直接用当轮榜单价、容忍滞后可达 5 分钟。滞后大的样本和精确样本在中位数里权重相同，这一列是用来判断混入程度的。

## 运行

服务器上已经装好 systemd 用户单元，不需要手动跑：

```bash
systemctl --user status meme-radar.service meme-radar-snapshot.timer
```

手动抓一次 / 出报表：

```bash
cd ~/meme-radar && .runtime/node-v22.23.1-linux-x64/bin/node ops/snapshot.mjs
cd ~/meme-radar && .runtime/node-v22.23.1-linux-x64/bin/node ops/analyze.mjs
```

## 这套数据能回答和不能回答什么

**能回答：**
- 16 道 check 里哪几道是瓶颈，以及瓶颈是数据问题还是币的问题
- 通过组与拒绝组的中位涨跌差异，带幸存者偏差的上下界
- 取价管线的健康度（滞后分布、缺失率、限流频率）

**不能回答：**
- 这套筛选能不能赚钱。统计里没有滑点、没有手续费、没有可成交性，也没有仓位管理
- 「系统整体是否有效」。拒绝组只覆盖**实际深审过**的币，回答的是「深审这 6 次请求有没有增量价值」，不是「从所有新币里选币的能力」
- 任何 50 个完成样本以下窗口的结论。meme 收益方差极大，50 个样本的中位数置信区间宽到难以区分两组
